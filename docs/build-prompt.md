## 2. Hard rules

These come from the owner and are not negotiable. The guard script in section 23 enforces the mechanical ones.

### 2.1 Never

- No purple, violet, fuchsia, or indigo anywhere: not in UI, not in the 3D scene, not in emails, not in the favicon. No colored gradients at all. The only permitted gradients are fades from transparent to the page background color, used to blend the 3D canvas into content.
- No "shift" buttons: buttons do not move, scale, tilt, slide a highlight, animate a gradient border, or follow the pointer. Hover changes background color or border color only, over 150 ms.
- No fake reviews, testimonials, client logos, star ratings, "trusted by" strips, or quotes. If the owner later supplies real, permissioned testimonials, they go in a content file with a `permission: true` field; the UI for them is not built in this pass.
- No fake metrics: no "500+ projects", "10x faster", "99.9% uptime", "4.9 rating", counters, or statistics of any kind unless the owner supplies the figure and its source in a content file.
- No big hero text. The largest heading on the site renders at 44 px on desktop and 32 px on mobile. The 3D scene carries the visual weight; the type stays calm.
- No emoji anywhere, including icons, bullet points, emails, admin UI, commit messages, and documentation. Icons come from `lucide-react` only.
- No em dashes (U+2014) or en dashes (U+2013) in any user-facing text, code comments, emails, or documentation. Use a comma, a period, a colon, or the word "to" for ranges ("2 to 4 weeks").
- No over-the-top scroll animation: no parallax on text, no per-section fade-and-slide entrances, no pinned horizontal scroll sections, no number counters, no text that scrambles or types itself, no marquee strips. The single scroll-driven effect on the site is the 3D camera (section 5).
- No AI stock photography or AI-generated illustrations. No stock photography at all. Imagery is limited to: the 3D scene, self-made SVG, real photos the owner supplies (team, office, real work), and real screenshots of real work with permission.
- No AI slop copy. Section 7 lists banned vocabulary and the writing rules.
- No custom cursor, cursor trail, cursor spotlight, magnetic hover, or `mix-blend-mode: difference` cursor tricks.
- No template or generator branding: remove the Next.js and Vercel SVGs, the "Create Next App" metadata, and any "Built with", "Made with", "Powered by", or AI-tool attribution. Set `poweredByHeader: false` in `next.config.ts`.
- No lorem ipsum, no `TODO` or `FIXME` left in `src/`, no commented-out code, no unused exports.

### 2.2 Always

- Dark theme only, with `color-scheme: dark` declared. Legal and admin pages are dark too, with body text contrast at or above 7:1.
- Sentence case for every heading, label, and button. No all-caps eyebrow labels.
- Every call to action names the thing that happens: "Start a project", "Send and verify", "Resend code", never "Submit" or "Learn more".
- Every page has unique `title`, `description`, canonical URL, Open Graph image, and JSON-LD where relevant (section 19).
- Every form field has a visible label, an associated error message, and keyboard operability. Every interactive element has a visible focus ring.
- `prefers-reduced-motion` turns off the page-load reveal and freezes the 3D camera (section 5.4).
- Everything that can fail has a defined failure state the user can act on (section 18).

## 4. Brand and design system

### 4.1 Direction

Two references define the taste level, and nothing from either is copied:

- From the Kage landing page (ThreeUI): one continuous dark 3D world, warm practical light sources against a cool dark volume, a camera that moves with scroll, and a quiet UI layer floating over it. We take the idea of a single authored scene, not its temple, moon, or typography.
- From curriculo.me: a dense but calm navigation with a mega menu, plain copy that explains instead of sells, a complete page hierarchy including comparisons, resources, and legal, and consistent components. We take the information architecture discipline, not its palette, logo, or content.

Design concept: "one light". Everything on the site is lit by a single warm lamp inside the 3D scene. The accent color in the UI is that lamp's color. Nothing else glows. The boldness budget is spent entirely on the 3D world; every other element is disciplined and conventional.

## 5. The 3D experience

### 5.1 Concept: the build floor

The home page sits over a single authored Three.js world: a dark workshop volume lit by one warm lamp. As the visitor scrolls, the camera travels along a fixed path past five "stations", one per service line, and each station's object assembles or resolves as the camera arrives. The DOM copy for each section scrolls over the canvas in a left-aligned column; the right two thirds of the viewport are left open so the scene is visible.

Nothing in the scene is a literal logo or brand (no WhatsApp glyph, no phone handset with a brand, no browser chrome). All geometry is procedural and instanced; there are no downloaded GLB models, HDRIs, or textures, so there are no licensing questions and no large asset downloads.

### 5.2 Scenes (stations) and what the camera does

The scroll range of the home page maps to `progress` in `[0, 1]`. Six keyframes on a `CatmullRomCurve3` camera path and matching `lookAt` targets define the journey. Each station below lists its progress window, the object, and the transition that plays as `progress` crosses it. All transitions are smoothstep eases of a single `t` uniform per station, computed from `progress`, so they scrub both directions and never get out of sync with the scroll.

| Station | Progress | Object | What happens as the camera arrives |
| --- | --- | --- | --- |
| 0 Hero | 0.00 to 0.15 | A 24 x 14 x 1 lattice of small instanced cubes (3 cm each in scene units) floating as a loose cloud | On load, the cloud drifts slowly (0.02 rad/s). As progress rises, each cube lerps from a seeded random position to its grid slot, forming a solid slab. The lamp sits up-left; the slab catches its edge light. |
| 1 Web | 0.15 to 0.35 | The slab | The slab thins to a pane (scale z from 1 to 0.06), its face takes a glass material (transmission 0.9, roughness 0.15, thickness 0.4, ior 1.5, no color), and a 12 x 8 grid of thin lines draws on its surface using a line shader with a `drawProgress` uniform. Camera moves to a three-quarter view. |
| 2 App | 0.35 to 0.55 | The pane | The pane shrinks to a 9:19.5 rounded rectangle (drei's `RoundedBox`), rotates 12 degrees about Y, and a second rectangle duplicates behind it at 60 percent opacity to suggest a stack of screens. Camera orbits 20 degrees. |
| 3 Automation | 0.55 to 0.75 | 48 instanced spheres (nodes) and 70 line segments (edges) | The rectangles dissolve into nodes (cubes shrink, spheres grow at the same positions). Edges draw between nodes. Pulses (small bright segments) travel along edges, driven by `time` in the shader, rate 1 pulse per 1.6 s per edge, staggered. Two nodes at the far ends brighten in alternation to suggest a message arriving and a reply going out. |
| 4 Marketing | 0.75 to 0.92 | 2,000 instanced points (desktop) / 700 (mobile) | The network's node positions seed an expanding field: points spread outward from the network's center along a gentle paraboloid, density highest at the center. Camera pulls back and rises. |
| 5 Close | 0.92 to 1.00 | Everything | Points fall back into a single calm slab, identical to the one formed in station 0 but lit from the front. Camera settles level. |

Lighting: one `SpotLight` (color `#F0B35A`, intensity tuned so highlights read without blowing out, penumbra 0.6, cast shadows off), one very dim cool `HemisphereLight` (sky `#1A2130`, ground `#0B0E13`), and a procedural `Environment` from drei built from two or three `Lightformer`s (resolution 256) for the glass reflections. Fog: `FogExp2` in ink color, density 0.045, so distant geometry fades into the page background.

Materials: `MeshStandardMaterial` (roughness 0.55, metalness 0.1, color `#2A3140`) for cubes and nodes; `MeshPhysicalMaterial` for the one glass pane; `LineSegments` with a custom `ShaderMaterial` for edges and surface lines; `Points` with a custom `ShaderMaterial` (size attenuation, round sprite via `gl_PointCoord`) for the field. Nothing emits a color other than lamp or fog tints.

### 5.3 Architecture

```
src/components/three/
  SceneCanvas.tsx          client component; dynamic import (ssr: false) of the Canvas; fixed inset-0 -z-10 pointer-events-none
  Scene.tsx                composes lights, fog, environment, CameraRig, stations
  CameraRig.tsx            reads scene store progress, lerps, places camera on the curve
  stations/
    LatticeSlab.tsx        station 0 and 5
    GlassPane.tsx          station 1 and 2
    Network.tsx            station 3
    Field.tsx              station 4
  materials/
    edgeLine.material.ts   shader for drawn lines and pulses
    fieldPoints.material.ts
  hooks/
    useStationT.ts         maps progress window to a smoothstep t
    useQuality.ts          picks quality tier (section 5.4)
  constants.ts             keyframes, counts per tier, colors (read from CSS tokens at mount)
  StationObject.tsx        the small single-station render used on service pages
```

Rules:

- One `<Canvas>` per page, mounted once in the home layout, never per section.
- `progress` lives in the Zustand `sceneStore` (section 17). A `useScrollProgress` hook in `src/hooks` listens to `scroll` (passive) and `resize`, computes `scrollY / (scrollHeight - innerHeight)` for the home page, and writes it to the store at most once per animation frame. `CameraRig` reads it inside `useFrame` and lerps a local value toward it with a damping factor of 0.08 per frame at 60 fps (use `THREE.MathUtils.damp` with delta time so it is frame-rate independent).
- Each home section element carries `data-station="hero|web|app|automation|marketing|close"`. An `IntersectionObserver` sets `activeStation` in the store; this is used only for analytics and for the service blocks' "current" styling, never to drive the camera (the camera follows continuous progress).
- The Canvas is mounted after first paint: render the page, then mount `SceneCanvas` inside a `useEffect` that waits for `requestIdleCallback` (fallback `setTimeout` 200 ms). Until then the page shows the ink background. There is no spinner and no "loading 3D" message.
- `frameloop="always"` while the home page is visible; switch to `"never"` when `document.visibilityState !== "visible"` or when the user has scrolled past the last station and the camera has settled (within 0.0005 of target).
- The scene reads the color tokens from `getComputedStyle(document.documentElement)` once at mount so the 3D palette and the CSS palette cannot drift.

### 5.4 Performance tiers and fallbacks

`useQuality` picks a tier once at mount and exposes it to the scene:

| Tier | Condition | Settings |
| --- | --- | --- |
| high | desktop, `hardwareConcurrency >= 8`, `devicePixelRatio <= 2` | dpr `[1, 1.75]`, full instance counts, glass transmission on, `AdaptiveDpr` active |
| medium | any other desktop, or mobile with `hardwareConcurrency >= 6` | dpr `[1, 1.25]`, 70 percent instance counts, glass transmission off (use a thin `MeshStandardMaterial` with opacity 0.6) |
| low | mobile with `hardwareConcurrency < 6`, or `navigator.connection.saveData`, or `prefers-reduced-motion` | dpr 1, 40 percent instance counts, camera fixed at the hero keyframe, station transitions still scrub but the camera does not move |
| none | WebGL 2 unavailable, or Canvas creation throws | No canvas. The page renders a static inline SVG of the slab outline in line color at 20 percent opacity behind the hero. All copy and layout are unchanged. |

Additional rules:

- Wrap the Canvas in an error boundary; any runtime error in the scene downgrades to tier `none` and logs once (section 18). The marketing page must never be blocked by the scene.
- Use drei's `PerformanceMonitor`; on two consecutive `decline` events, step the tier down one level at runtime.
- Budget: the 3D chunk (`three`, `@react-three/fiber`, `@react-three/drei`, scene code) stays under 450 KB gzipped and loads only on the home page and service pages. Import drei components individually. Do not import `@react-three/postprocessing`; there is no post-processing.
- Target 60 fps on a 2022 mid-range laptop at tier high and 30 fps or better on a 2021 mid-range Android phone at tier medium. Measure with the browser's performance panel before calling the phase done.

### 5.5 Service page station objects

Each service page shows its station object alone in a 4:3 panel (ink-2 background, line border, radius 10) to the right of the page lead on desktop and below it on mobile. The object rotates slowly (0.15 rad/s) and does not respond to scroll. `frameloop="demand"` with an interval-driven invalidate at 30 fps keeps CPU use low. Tier rules from 5.4 apply; tier `none` shows the same inline SVG fallback.

### 5.6 Do and do not

- Do keep the scene legible at a glance: one object in focus per station, generous negative space, fog hiding the rest.
- Do keep everything procedural and deterministic (seeded random via a tiny mulberry32 implementation in `src/lib/random.ts`) so the scene renders identically on every load.
- Do not add floating particles everywhere, lens flares, bloom, chromatic aberration, scanlines, grain overlays, or a grid floor. None of those.
- Do not put text in the 3D scene. All text is DOM text.
- Do not let the scene intercept pointer events.

## 7. Copy rules

Apply these to any text you write that is not provided above, including microcopy, emails, errors, admin labels, and documentation.

- Plain verbs, short sentences, sentence case. Say what a thing is or does; do not sell it.
- Every claim is something the business can be held to, not a superlative. "Weekly demos" is a claim. "Unmatched quality" is not.
- No numbers, dates, names, or prices that did not come from the owner.
- Buttons and links name the outcome: "Start a project", "Confirm", "Resend code", "Go to home".
- Errors say what happened and what to do next, in one or two sentences, without apologizing: "That code has expired. Request a new one." Empty states invite an action.
- No rhetorical questions in headings, no "Welcome to", no "Let's", no exclamation marks.
- Banned vocabulary (the guard checks these, case-insensitive): seamless, seamlessly, cutting-edge, next-gen, next-generation, unlock, elevate, empower, supercharge, revolutionize, revolutionise, game-changing, game changer, leverage, synergy, best-in-class, world-class, state-of-the-art, unleash, transform your, delve, harness, effortless, innovative solutions, tailored solutions, holistic, bespoke, passionate about, dedicated team, trusted partner, end-to-end solutions, digital transformation journey, 360-degree.
- Replace "AI-powered" with what the thing actually does ("answers on WhatsApp", "summarizes the call").

## 12. Backend: API structure

### 12.1 Conventions

- Public mutations are route handlers under `/api/v1` so other systems (the agency's own WhatsApp bot, a future mobile app) can use them. Admin mutations are server actions in `features/*/actions.ts`, guarded by `requireAdmin()`.
- Every handler: parse and validate with the feature's Zod schema; check rate limit; call the service; map the `Result` to a response with `ok()` / `fail()` from `src/lib/http.ts`. No business logic in route files.
- Response envelope, always JSON, always one of:

```json
{ "ok": true, "data": { ... } }
{ "ok": false, "error": { "code": "VALIDATION_ERROR", "message": "Email is required.", "details": { "fieldErrors": { "email": ["Required"] } } } }
```

- Error codes and HTTP status: `VALIDATION_ERROR` 400, `UNAUTHORIZED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `CONFLICT` 409, `RATE_LIMITED` 429 with `Retry-After`, `VERIFICATION_INVALID` 400, `VERIFICATION_EXPIRED` 410, `VERIFICATION_LOCKED` 423, `BOT_CHECK_FAILED` 400, `DB_ERROR` 500, `EMAIL_ERROR` 502, `INTERNAL` 500. Internal messages are never leaked; 5xx responses carry a generic message and a `requestId`.
- Every request gets a `requestId` (`crypto.randomUUID()`) returned in the `x-request-id` header and included in logs.
- Mutating handlers verify the `Origin` header matches `NEXT_PUBLIC_SITE_URL` (or the preview URL) unless the request carries a valid `x-api-key`.
- Versioning: new breaking changes go in `/api/v2`; `/api/v1` is never changed incompatibly.

### 12.2 Endpoints

| Method and path | Auth | Rate limit | Purpose |
| --- | --- | --- | --- |
| `GET /api/v1/health` | none | 60/min per IP | `{ status: "ok", version, db: true }`; runs `select 1` |
| `GET /api/v1/forms/token` | none | 30/min per IP | Returns `{ token }`, an HMAC-signed timestamp the form must send back (section 16) |
| `POST /api/v1/leads` | origin check, form token, honeypot, Turnstile if enabled | 5 per hour per IP, 3 per hour per email | Create a lead in `pending_verification`, create and send a code. Returns `{ leadId, email, resendAvailableAt }` |
| `POST /api/v1/leads/verify` | origin check | 10 per 10 minutes per IP | Body `{ leadId, code }`. Verifies, marks lead `new`, triggers notifications in `after()`. Returns `{ verified: true }` |
| `POST /api/v1/leads/resend` | origin check | 3 per hour per lead, 60 s cooldown | Issues a new code, invalidates the old one |
| `POST /api/v1/integrations/leads` | `x-api-key` = `LEADS_API_KEY` | 60/min per key | Create an already-verified lead (`source: "api"`, `email_verified_at` now) from a trusted system. Returns `{ leadId }` |
| `GET /api/v1/admin/notifications/unread-count` | admin session | 120/min | `{ count }` for the header badge, polled every 30 s |
| `POST /api/v1/cron/cleanup` | `Authorization: Bearer CRON_SECRET` | none | Deletes unverified leads older than 7 days, consumed or expired verifications older than 1 day, rate-limit rows older than 24 hours. Scheduled daily in `vercel.json` |

### 12.3 Services and the Result type

```ts
// src/lib/result.ts
export type Result<T, E = AppError> = { ok: true; data: T } | { ok: false; error: E };
export const ok = <T>(data: T): Result<T, never> => ({ ok: true, data });
export const err = <E>(error: E): Result<never, E> => ({ ok: false, error });
```

Services never throw for expected failures; they return `Result`. They throw only for programmer errors. Route handlers and server actions catch everything else once, at the edge, and map to `INTERNAL`.

Document every endpoint in `docs/api.md` with request, response, and error examples (section 24).

## 13. Email verification flow

The purpose is a real, reachable email on every lead, so the team never chases typos or bots.

1. Client submits the form with the form token it fetched on mount. Server validates the body, verifies the token's signature and age (section 16), checks the honeypot (any value returns a fake success to the bot and no lead is created), verifies Turnstile if enabled, checks rate limits, and normalizes the email (trim, lowercase).
2. In one transaction: insert the lead (`pending_verification`), insert a verification row, write a `created` event.
3. Code: `crypto.randomInt(0, 1_000_000)` zero-padded to 6 digits. Stored as `HMAC-SHA256(code, VERIFICATION_PEPPER)` hex. Expires 10 minutes after creation. Never logged, never returned in any response, never stored in plain text.
4. Email the code with the `VerificationCode` template: subject "Your Getwithus verification code: 123456" `[OWNER: brand]`, a one-line explanation, the code in large text, "Expires in 10 minutes. If you did not request this, ignore this email." Plain-text alternative included. From `EMAIL_FROM`, reply-to `EMAIL_REPLY_TO`.
5. Client enters the code. Server loads the newest unconsumed verification for the lead. Compare with `crypto.timingSafeEqual` on the hashes. On mismatch, increment `attempts`; at `max_attempts` mark it consumed and return `VERIFICATION_LOCKED` (the client offers "Resend code"). On expiry return `VERIFICATION_EXPIRED`. On success: mark consumed, set `email_verified_at`, status `new`, write a `verified` event, and in `after()` dispatch notifications (section 14) and send the `LeadConfirmed` email to the client.
6. Resend: allowed after 60 seconds, at most 3 per hour per lead; creating a new code marks previous rows consumed. The client shows a countdown using `useCountdown`.
7. "Use a different email" on the client simply resets to the form with values kept; the abandoned pending lead is removed by the cleanup cron after 7 days. Do not expose any endpoint that deletes leads from the public site.
8. Development: with `EMAIL_TRANSPORT=console`, the email client prints the rendered email (including the code) to the server console and nowhere else.

Client-side, the whole flow is a state machine inside `LeadForm` / `BriefWizard`: `editing` to `submitting` to `verifying` (with sub-states `idle`, `checking`, `error:<code>`) to `done`. Errors map to copy:

| Code | Copy |
| --- | --- |
| `VERIFICATION_INVALID` | "That code is not correct. Check the email and try again." plus remaining attempts when 2 or fewer remain |
| `VERIFICATION_EXPIRED` | "That code has expired. Request a new one." |
| `VERIFICATION_LOCKED` | "Too many attempts. Request a new code to continue." |
| `RATE_LIMITED` | "Too many requests from this connection. Try again in a few minutes." |
| `EMAIL_ERROR` | "We could not send the email right now. Try again, or email us directly at `[OWNER: hello@domain]`." |
| anything else | "Something went wrong on our side. Try again, or email us directly at `[OWNER: hello@domain]`." |

## 14. Notification system

## 16. Security

- Security headers from `src/proxy.ts` (or `headers()` in `next.config.ts`; pick one and document it): `Content-Security-Policy` with `default-src 'self'`, `script-src 'self' 'unsafe-inline'` only if the Plausible script or Turnstile require it (prefer a nonce if the installed Next version supports it cleanly; verify), `img-src 'self' data: blob:`, `connect-src 'self'` plus the analytics and Turnstile origins when enabled, `frame-src` Turnstile only when enabled, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`; `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`; `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `Permissions-Policy: camera=(), microphone=(), geolocation=()`; `X-Frame-Options: DENY`. Test that the 3D scene still runs under the CSP (WebGL needs nothing special; `blob:` covers worker and texture URLs if any).
- Input validation on every boundary with Zod; lengths capped; URLs validated; emails normalized. Output encoding is handled by React; never use `dangerouslySetInnerHTML` except for the JSON-LD script, whose content is `JSON.stringify`ed from typed objects.
- Rate limiting (section 12.2) keyed by `sha256(ip + daily salt)` so raw IPs are not stored. `getClientIp` reads `x-forwarded-for` first IP on Vercel; document the assumption.
- Bot defenses: honeypot field; a form token fetched from `GET /api/v1/forms/token` when the form mounts (an HMAC-signed timestamp using `VERIFICATION_PEPPER`), which the server requires on every lead submission and rejects when younger than 3 seconds or older than 2 hours; and Cloudflare Turnstile when configured.
- Secrets never reach the client bundle: only `NEXT_PUBLIC_*` variables are exposed, enforced by the env schema.
- Cron and integration endpoints compare secrets with `timingSafeEqual`.
- Dependencies: enable Dependabot or Renovate in `.github`; run `pnpm audit --prod` in CI and fail on high severity.
- Logging never includes verification codes, full emails of clients in production logs (mask as `j***@domain`), tokens, or request bodies.

## 17. State management

Keep state where it belongs and nowhere else.

- Server state (leads, notifications) stays on the server: server components read it; server actions mutate it; `router.refresh()` or `revalidatePath` after mutations. No client-side cache library.
- URL state (admin filters, pagination, `?next=` on login) lives in `searchParams`.
- Form state lives in `react-hook-form`.
- Cross-component client state lives in two Zustand stores, each small and typed:
  - `scene.store.ts`: `progress: number`, `activeStation`, `quality`, `reducedMotion`, `canvasReady`, with setters. ## 18. Error handling conventions

- `src/lib/errors.ts` defines `AppError` (`code`, `message`, `status`, `details?`, `cause?`) with factory functions per code. All services return `Result<T, AppError>`.
- Boundaries that catch everything, once: route handlers (`withHandler` wrapper in `src/lib/http.ts` that assigns `requestId`, catches, logs, maps), server actions (`withAction` wrapper returning a serializable `Result`), the admin layout and marketing layout via `error.tsx`, the 3D canvas via a React error boundary that downgrades the tier.
- `src/lib/logger.ts`: `info`, `warn`, `error` emitting JSON in production and readable lines in development, always including `requestId` when available. No `console.log` elsewhere (ESLint `no-console` with `logger.ts` excepted).
- Every `fetch` to a third party (Resend, Slack, WhatsApp, Turnstile) uses `AbortSignal.timeout(5000)`, checks `response.ok`, and converts failures to `AppError`.
- Every `await` on the database is inside a repository `try/catch`.
- Client fetches use a small `apiClient` in `src/lib/http.ts` that parses the envelope and returns `Result`; components switch on `error.code` to pick copy (section 13 table) and show it inline next to the control that caused it, with a toast only for actions that have no inline place.
- `error.tsx` shows a reference ID (the `requestId` or `digest`) the user can quote; the same ID appears in the server log line.
- No empty `catch` blocks. No `catch (e) { return null }` without a logged reason.

## 23. Quality guard script

`scripts/guard.mjs` scans everything under `src/` (which includes `src/content` and the email templates) and exits non-zero on any match. It runs as the first step of the `build` script, so a production build cannot ship a violation. `GUARD_STRICT=1` adds the owner-placeholder rule for launch.

```js
// scripts/guard.mjs
import { readdirSync, readFileSync, statSync } from "node:fs";
import { join, extname, relative } from "node:path";

const ROOTS = ["src"];
const EXTENSIONS = new Set([".ts", ".tsx", ".css", ".md", ".mdx", ".json"]);
const SKIP_DIRS = new Set(["node_modules", ".next", "migrations"]);
const strict = process.env.GUARD_STRICT === "1";

const rules = [
  { name: "em or en dash", re: /[\u2013\u2014]/g },
  { name: "emoji", re: /[\u{1F300}-\u{1FAFF}\u{1F900}-\u{1F9FF}\u{2600}-\u{27BF}\u{1F600}-\u{1F64F}\u{1F680}-\u{1F6FF}]/gu },
  { name: "purple family token or utility", re: /\b(purple|violet|fuchsia|indigo)-\d{2,3}\b|--color-(purple|violet|fuchsia|indigo)\b/g },
  { name: "colored gradient stop", re: /\b(from|via|to)-(red|orange|amber|yellow|lime|green|emerald|teal|cyan|sky|blue|indigo|violet|purple|fuchsia|pink|rose)-\d{2,3}\b/g },
  { name: "template or generator branding", re: /next\.svg|vercel\.svg|Generated by create next app|Create Next App|\bBuilt with\b|\bMade with\b|\bPowered by\b/g },
  { name: "placeholder text", re: /lorem ipsum|\bTODO\b|\bFIXME\b/gi },
  { name: "fake social proof", re: /\btestimonials?\b|\btrusted by\b|\brated \d|[\u2605\u2B50]|\b\d+(\.\d+)?x (faster|more|better)\b|\b\d{2,}\+ (clients|customers|projects|companies|businesses)\b/gi },
  { name: "custom cursor", re: /CustomCursor|cursor-none|mix-blend-difference|magnetic/gi },
  { name: "slop vocabulary", re: /\b(seamless(ly)?|cutting[- ]edge|next[- ]gen(eration)?|unlock|elevate|empower(ing)?|supercharge|revolutioni[sz]e|game[- ]chang(ing|er)|leverage|synerg(y|ies)|best[- ]in[- ]class|world[- ]class|state[- ]of[- ]the[- ]art|unleash|transform your|delve|harness|effortless(ly)?|innovative solutions|tailored solutions|holistic|bespoke|passionate about|dedicated team|trusted partner|end[- ]to[- ]end solutions|digital transformation journey|360[- ]degree)\b/gi },
  { name: "forbidden motion library import", re: /from ["'](gsap|lenis|@studio-freight\/lenis|aos|locomotive-scroll|framer-motion)["']/g },
];
const strictRules = [{ name: "owner placeholder", re: /\[OWNER:/g }];

function walk(dir, out = []) {
  for (const entry of readdirSync(dir)) {
    if (SKIP_DIRS.has(entry)) continue;
    const full = join(dir, entry);
    const st = statSync(full);
    if (st.isDirectory()) walk(full, out);
    else if (EXTENSIONS.has(extname(entry))) out.push(full);
  }
  return out;
}

const files = ROOTS.flatMap((root) => walk(root));
const active = strict ? [...rules, ...strictRules] : rules;
const violations = [];

for (const file of files) {
  const text = readFileSync(file, "utf8");
  const lines = text.split("\n");
  for (const rule of active) {
    lines.forEach((line, i) => {
      rule.re.lastIndex = 0;
      if (rule.re.test(line)) violations.push(`${relative(process.cwd(), file)}:${i + 1}  ${rule.name}`);
    });
  }
}

if (violations.length) {
  console.error(`Guard found ${violations.length} violation(s):\n` + violations.join("\n"));
  process.exit(1);
}
console.log(`Guard passed (${files.length} files${strict ? ", strict" : ""}).`);
```

Notes: `src/server/db/migrations` is skipped because generated SQL is not user-facing. If a rule produces a false positive in a legitimate technical context, fix the text rather than weakening the rule; if that is impossible, add a narrowly scoped exception with a comment explaining it. The word "ecosystem" is deliberately not in the list; avoid it in copy anyway.
